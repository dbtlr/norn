# 0017 — Registered vaults, summoned owners: always-routed access, disposable derivation, owner-held trust

**Decision:** norn addresses vaults **by registered name** through a bidirectional registry (name → root, root → name; CWD resolution is sugar). **Every invocation routes to a daemon** — the CLI never opens a cache in-process; a daemon is *summoned* on demand (ephemeral tier for unregistered vaults and all dev builds; resident tier for registered vaults; managed tier for supervised installs/HTTP MCP) and reaps itself after an idle TTL. **Registration gates all durable artifacts** (persistent cache entry, event stream, logs); unregistered work is tmp-homed and disposable. The **SQLite cache db is pure derivation** — created at summon, deleted at owner exit, so client-vs-cache schema mismatch is unrepresentable. **Trust is maintained, not proven**: a file watcher (fast path) plus a drift auditor (truth loop, health metrics) carry the burden of proof between requests; the request path presumes a warm vault is valid. Design of record: *the registered-vault architecture note (internal design doc)*.

## Context

The 2026-07-17 evidence chain (a +461-entries-per-test-run leak, a day-long race chain, a 61k-entry / 8 GB consumer leak) traced every active bug class to one premise: the cache as a global, ambient, shared-mutable tree written by uncoordinated processes, each entry's lifecycle bound to nothing. The founding "safety > speed" bias — re-prove freshness on every request — was correct pre-daemon (every invocation cold, nothing guarding files between calls) and wrong after: it makes the daemon an over-engineered passthrough, performant to date only because vaults were small. The placement itself (`~/.cache/<hash>`) was an unshaped artifact of founding commit `be02575`, not a decision.

## Load-bearing choices

- **Identity is assigned, never derived.** The registry assigns vault identity; nothing infers it from CWD, canonical paths, or environment. (the "identity travels with the artifact" principle applied at vault altitude — and required by the HTTP MCP roadmap, where off-system consumers cannot know directories.)
- **Registration is explicit, never implicit.** Consumers call it programmatically as a stable setup artifact; implicit registration would recreate the leak class inside the registry.
- **One owner per entry, enforced by the existing lifetime flock** (ADR 0005). Dev builds run the ephemeral tier unconditionally (ADR 0012's fingerprint keys the socket), so a dev binary structurally cannot touch registered entries.
- **The invariant is relocated, not abandoned.** Verification moves off the request path into owner machinery; the drift auditor is the "don't skip" half of trust-over-speed. Observed drift ≈ 0 is what licenses presumption; observed drift > 0 is a watcher bug surfacing as a metric, not as wrong results.
- **Warm-up-on-summon is the accepted cost** (~linear in vault size; ~500ms/1.2k docs today). Mitigations: progress surface on self-update and warming queries; managed tier for those who never want cold starts. A future opt-in non-ephemeral db model is the named escape hatch, deliberately deferred.

- **Uncertainty fails closed.** When the watcher or drift auditor cannot vouch for a vault (event overflow, an unsupported backend, auditor lag), the owner drops the presumption of validity for that vault and re-proves freshness before serving the next request — degraded means slower, never stale.

## Reversals and amendments (owned explicitly)

- **Reverses ADR 0016's rejection of "always-route-to-daemon (kill the cold path)."** What changed: 0016 evaluated routing as an *accelerator* while trust still lived in per-request proofs, so a cold path had to stay budget-compliant. Once trust moves into the owner, a non-routed path is not a cheaper equivalent — it is an untrusted parallel implementation. 0016's seam (adapter → dispatch → execute) survives intact; its dispatch answers "summoned or resident," never "routed or direct."
- **Amends ADR 0005:** the daemon ceases to be an optional accelerator and becomes the sole access path; verify-once-hold-warm becomes verify-once-**watch-thereafter**. The lifetime flock and one-host-N-contexts topology carry forward unchanged.
- **Amends ADR 0006:** the registry gains its authoritative role (identity + durability gate), beyond client-side name resolution.
- **Amends ADR 0013:** the generational/writer machinery and control-plane liveness contract carry forward inside the owner, but its Direct escape hatches (no pong, stalled writer → Direct) are superseded — no owner means summon; there is no direct path.
- 0001–0004, 0007–0015 are relitigated separately in the redefinitional grooming pass; supersessions land as explicit status changes, not silence.

## Consequences

- The leak, race, skew, and identity-war bug classes are prevented by construction; the prune/sweep/marker apparatus, multi-schema db matrix, channel-in-path machinery, and per-request freshness proofs are **deleted, not improved**.
- The daemon becomes load-bearing infrastructure: summoning must be robust headless, orphan owners must be detectable (flock + TTL), and crash blast radius is all-vaults-cold-until-resummoned (automatic).
- Registration becomes public consumer contract (a consumer adopts on its pinned-upgrade schedule per ADR 0016's elective-coupling doctrine).
- The task queue and workspace notes predating this decision are suspect until re-vetted; the redefinitional grooming pass is part of this decision's execution.

## Amendment — 2026-07-25: the owner socket is keyed by the vault config too

An owner loads `.norn/config.yaml` once, at warm-up, and serves every later request under that in-memory schema. Keying its socket by the vault root and build fingerprint alone therefore made the config a *sticky* input: a config created or edited after an owner warmed stayed invisible for the rest of the idle TTL, so `find` / `get` / `count` / `validate` and the `set` / `new` write path all kept running under the previous schema — enforcement the edited config declares silently did not fire, and a config that fails to load reported nothing.

The socket name now folds the config file's **content hash** into its identity segment (`crates/norn-client/src/addr.rs`), alongside the canonical root and the build fingerprint. A created, edited, or removed config addresses a different owner, so the next invocation summons one that reads the config from disk; the owner holding the previous revision is orphaned to idle out — the same trade the build fingerprint already makes on a rebuild. Content hashing (not `(mtime, size)`) keeps a same-bytes rewrite from orphaning a warm owner and keeps a same-size edit inside one mtime tick from being missed. A config present but unreadable (permissions, a directory in the file's place, an override path pointing at nothing) takes a *third* identity, distinct from both a content hash and the no-config identity: the owner treats it as a hard error, and collapsing it onto "no config" would let a warm defaults-owner answer exit 0 where a cold owner exits 1.

Every addressing via must derive the same config for one root, or the keying itself manufactures the split it exists to prevent. `-C <root>` and `NORN_ROOT` resolve with no registry entry attached, so the `[vaults.<name>].config` override is reverse-looked-up from the canonical root rather than read off the resolved entry — the treatment durable telemetry (NRN-400) already used, and for the same reason. An unreadable registry now REFUSES (exit 1) rather than degrading to "unregistered": silently downgrading a registered vault to defaults drops the very schema override the lookup exists to supply, so a write the vault's real schema forbids would land at exit 0. The `--vault <name>` and directory-binding vias already failed loud on the same read; refusing converges all four.

**This restates "one owner per entry" as one owner per `(vault root, build fingerprint, config identity)`.** N owners over one vault is a normal transient state, not a violated invariant — a rebuild window, or the window between a config edit and the previous owner's idle reap. The consequences, owned:

- **Writes.** Each owner holds its own single-writer lock, so the serialization boundary is per owner, not per vault. A cross-owner write lands on the applier's foreign-writer path, which branches by `DriftPolicy`: a purely DECLARATIVE edit (set / add / remove frontmatter — the dominant cross-owner case) re-runs against the other owner's bytes, bounded, and lands; a content-anchored edit (`str_replace`, section/heading ops, `rewrite_link`, `replace_body`) refuses `concurrent-modification` outright, since re-landing on drifted content would destroy the external edit. A plan carrying a `document_hash` refuses either way (`stale-document-hash`). Neither branch clobbers.
- **`{{seq}}` allocation and multi-file plan atomicity are per owner.** Two owners can allocate the same `{{seq}}` id concurrently; the loser's create finds the destination occupied and refuses `create-destination-exists` (loud, never a silent overwrite without `--force`).
- **Durable telemetry.** Two owners appending to one daily JSONL file can tear a line longer than `PIPE_BUF`; the reader skips unparseable lines (NRN-464).
- **Long-lived holders** (the MCP server) keep the owner — and therefore the schema and the writer lock — they connected with until they resummon. That is the dual-owner shape worth watching: two schemas, two writer locks, one vault (NRN-487).

**Alternative considered and deferred: owner step-aside.** The client sends its computed config identity in the connect handshake; the owner compares it against what it warmed under and, on mismatch, shuts down cleanly so the client resummons. That restores the per-vault flock invariant outright — one owner, always — at the cost of a wire field and a resummon round-trip inside a single invocation, and it does nothing for the build-fingerprint axis (which is keyed by address by deliberate ADR 0012 design). Deferred as a phase-4 candidate, to be weighed once the resident tier exists.
